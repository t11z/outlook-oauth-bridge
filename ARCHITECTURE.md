# Architecture

Design rationale and non-obvious constraints for `outlook-oauth-bridge`. Read `README.md` first for what the product does; this file is for anyone (human or AI) about to modify the code.

## Layout

```
src/
├── index.js    Bootstrap: preflight, first-run banner, wires smtp+queue+web, SIGTERM/SIGINT
├── shutdown.js Shared graceful-drain-then-exit(0), used by index.js's signal handlers and the GUI's restart endpoint
├── config.js   Env parsing + fixed constants (MAX_MESSAGE_BYTES, backoff table, etc.)
├── store.js    All filesystem I/O: state.json, spool, credentials, atomic writes — the trust anchor
├── events.js   In-process event bus + ring buffer (SSE feed) + stdout structured logging
├── mime.js     Pure functions: header parsing, From rewrite, sender selection, envelope/header recipient reconciliation
├── smtp.js     smtp-server wiring: auth, size gate, spool-then-accept, alias-path routing decision
├── oauth.js    Device code flow, token cache/refresh, single-flight, invalid_grant recovery, scope selection
├── graph.js    sendMail POST (single-call + alias-forcing draft path) + error classification (permanent/retryable/retryable-ambiguous/rate-limited/auth)
├── queue.js    Spool-is-the-queue: serial worker, backoff+jitter, dead-letter, injectable clock
└── web/
    ├── server.js   Router + static file serving (fixed 3-file allowlist)
    ├── session.js  HMAC-signed cookies (key derives from password hash), login throttling
    └── api.js      JSON endpoints + SSE
public/         index.html, app.js, style.css — no framework, no bundler
test/
├── fake-graph.js          Mocks login.microsoftonline.com + graph.microsoft.com
├── mime.test.js           Unit tests for mime.js's pure functions
├── sender-address.test.js Settings-API validation for senderAddresses/defaultSender/aliasForceFrom
└── e2e.test.js            Real SMTPServer + real web server + real queue, against the fake Graph
```

## Why the pieces are shaped this way

**mime.js processes each message exactly once, at receive time (in `smtp.spoolProcessedMessage`), not on every retry.** The `.eml` file on disk is already the Graph-ready payload — From rewritten, recipients reconciled, CRLF-normalized. This makes the SMTP `250` response an honest promise: what gets accepted is exactly what gets sent, even if the account or settings change before the queue gets to it later. Don't move mime processing into `queue.js` — it would make delivery non-deterministic relative to what was accepted. **This extends to which GRAPH SEND PATH a message takes, not just its bytes**: `smtp.spoolProcessedMessage`'s `aliasPathAvailable()` decides at spool time whether a message qualifies for the alias-forcing draft path in `graph.js`, and persists that decision as `sendAs` in the spool metadata. It has to be decided together with the bytes — the degraded fallback writes a different `Reply-To` (see `mime.processOutgoingMessage`'s `aliasReplyToInsurance` option) than the confirmed-alias case, and `graph.js` has no way to redo that choice on a later retry without re-running `mime.js`, which is exactly what this invariant forbids.

**`mime.selectSender` picks a sender by precedence — From: header, then SMTP envelope MAIL FROM, then a default — and never rejects an unlisted one, only skips it.** `session.envelopeFrom` (captured in `smtp.js`'s `onMailFrom`) existed before this feature and reached nothing but spool metadata; it's now the fallback candidate for devices that expose a "sender address" field but not `From:` header control. An address that matches nothing in the allowed set falls through to the default (today's only behavior, and still what happens with no aliases configured) rather than failing the send — rejecting would break every device already sending a hardcoded, unlisted `From:` like a printer's `printer@lan.local`. `rewriteFromHeader` itself didn't need to change its matching logic for this — it already no-ops when the header matches the address it's given; aliases just widen what address it's given from a single scalar (`accountAddress`) to whatever `selectSender` resolved.

**graph.js's `sendMail()` never throws.** It always resolves to `{ ok, class, code, message, retryAfterMs? }`. `queue.js` and `smtp.js`'s test-mail path both depend on this — a throwing `sendMail()` would need try/catch at every call site instead of one classification switch in `queue.js`'s `applyResult()`. This holds for both of its two send paths (see next).

**`graph.sendMail(mime, { from })` has two send paths, chosen by data, not policy.** `from: null` — the overwhelming majority of messages, since it requires `settings.aliasForceFrom` to be on AND the sender to be a verified, listed alias AND the connection to hold the `Mail.ReadWrite` scope — takes the original single-call `POST /me/sendMail`, byte-for-byte the same request this file made before aliases existed. That's what keeps the common case at zero regression risk from this feature. A non-null `from` takes a three-call path (create a MIME draft via `POST /me/messages`, `PATCH` its `from`, then `POST .../send`) — the only way to keep full MIME fidelity (attachments, custom headers) *and* set Graph's `from` property explicitly, since MIME-mode `sendMail` has no such property and JSON-mode `sendMail` would require fully parsing the relayed MIME into a `message` object (multipart boundaries, attachment re-encoding, charset handling) — a MIME parser this project deliberately doesn't carry. **This path is unverified against a real consumer account.** `PATCH /me/messages` documents `from` as updatable ("must correspond to the actual mailbox used" — an alias plausibly qualifies, since it's the same mailbox), but Microsoft has never confirmed this for personal-account aliases specifically, and at least one public report describes Graph silently keeping the primary address regardless of what's requested. So the PATCH's response is never trusted at face value: the returned `from` is read back and compared to what was asked for, and a mismatch is recorded (`oauth.aliasFromSupported = false`) rather than assumed — see `queue.js`'s `recordAliasOutcome`. Either way the draft is still sent: a degraded send (primary address, alias preserved as `Reply-To`) beats a dead letter over an API behavior nobody could confirm ahead of time.

**Two Graph permission scopes were considered for forcing an alias `From:` and one was rejected.** `Mail.Send.Shared` grants send-as/send-on-behalf for *other people's* mailboxes (delegate/shared-mailbox scenarios) — not aliases of your own mailbox — so it wouldn't help here and would cost the same forced re-consent as the scope actually used. `Mail.ReadWrite` (needed for the `PATCH` step above) is requested conditionally: `oauth.currentScope()` mirrors `currentClientId()`'s pattern exactly (one accessor, used by both the device-code request and the refresh request, so what's requested and what's granted can't silently disagree) and only adds `Mail.ReadWrite` when `settings.aliasForceFrom` is on. Scope is fixed at grant time — a refresh cannot silently widen it — so turning that setting on doesn't take effect until the user reconnects; `oauth.js` doesn't force `needs_reauth` when the setting flips, since that would take a working installation offline over an opt-in feature nobody asked to use yet.

**Per-alias SMTP credentials were considered and rejected.** `store.state.smtp` is a single `{ username, password }`; multiple credentials would turn `onAuth`'s two `timingSafeEqualStr` calls into a scan that has to stay constant-time regardless of which entry matched (or didn't) — a genuinely new correctness surface — and `authFailures`' IP-keyed ban tracking would need rethinking too, all to serve a narrow case (two devices, each with an unchangeable hardcoded `From:`, needing different senders) that `selectSender`'s envelope fallback already covers whenever either device lets you set `MAIL FROM`.

**`mime.formatDisplayName` strips `\r`/`\n` from a sender's display name, and that isn't a cosmetic normalization.** A device's own display name has already been collapsed to spaces by `unfoldHeaders`' folding logic by the time any of this code sees it. A sender's `displayName` from `settings.senderAddresses`, set through the web GUI, has not — `normalizeCrlf` only runs on the raw input *buffer*, before headers are rebuilt from parts, so an unstripped CR/LF here would be a genuine header injection via the web GUI, the one path into a header that isn't a device's own message. `web/api.js`'s `handleSettingsPatch` validates this on the way into `state.json` too; the strip in `mime.js` is defense in depth against a hand-edited `state.json`.

**queue.js's pause gate checks `oauth.status !== 'connected'` (positive), not an enumeration of bad statuses.** It used to check only `=== 'needs_reauth'`, which left a real gap: a message queued while `unconfigured` (e.g. the user disconnects with mail still queued) hit `graph.sendMail()`'s `class: 'auth'` result repeatedly with no backoff — a busy loop. The positive check closes that gap and any similar one that might appear if a new status value is ever added.

**`realClock.sleep(ms, signal)` in queue.js takes an `AbortSignal`.** `wake()` (used on stop, on reconnect, on manual "retry now") resolves the pending wait *promise* immediately, but without signal-based cancellation the underlying `setTimeout` — up to a 60s backoff wait — keeps running and keeps the process alive until it fires on its own. This stalled graceful shutdown and hung the e2e test suite until it was fixed; don't reintroduce a bare `setTimeout` here.

**`events.emitEvent(type, data)` merges `data` after its own `{ seq, type, at }`.** Do not rename the ring-buffer sequence field back to `id` — several event types (`queued`/`sending`/`sent`/`retry`/`dead`) pass their own semantic `id` (the spool message id) in `data`, and a caller-less event (like `auth`) would silently fall back to displaying the raw sequence number instead of nothing. This exact bug shipped once; the frontend's `pushFeedRow`/`feedMessage` in `public/app.js` depend on `seq` and `id` staying distinct.

**Settings split between fixed constants and live-editable state.** `MAX_MESSAGE_BYTES`, `MAX_RECIPIENTS`, `MAX_SENDER_ADDRESSES`, the backoff table, and attempt caps are fixed in `config.js` — they're tied to Graph's actual API limits or aren't meaningful user preferences. `fromRewrite`, `senderAddresses`, `defaultSender`, `aliasForceFrom`, `rateLimitPerMin/Day`, `maxQueueDepth`, `queueMaxAgeHours` live in `state.json.settings` and are read fresh from `store.state.settings` on every check in `queue.js`/`smtp.js` — no restart needed (though `aliasForceFrom` needs a *reconnect*, not a restart, to actually take effect — see the scope bullet above). `requireTls` and `smtpPort` are the exceptions: stored in `settings` (so the GUI can edit them) but only take effect on next boot, since both affect `smtp-server`'s construction/listen-time wiring, not something checked per-message.

**`oauth.state.aliasFromSupported` lives under `oauth`, not `settings`, and is cleared on both disconnect and switching accounts.** It's a property of the *connected mailbox* — what was observed when the alias-forcing send path was last exercised against it — not a user preference, so it doesn't belong in `settings` and the user can't edit it directly. `oauth.completeConnection()` clears `senderAddresses`/`defaultSender` too, but only when the newly connected account's address differs from the previously connected one: aliases belong to one specific mailbox, and silently carrying them over to a different one would turn every subsequent send into a `403 ErrorSendAsDenied` dead letter. A reconnect of the *same* account (the ordinary re-auth case) keeps them.

**`smtp.js`'s `start()` returns a promise, not the server, because a bad port has to fail as cleanly as a bad TLS config.** `net.Server.listen()` reports bind failures (e.g. `EACCES` on a privileged port like 587 without root/`CAP_NET_BIND_SERVICE`) asynchronously via an `'error'` event, not a synchronous throw — with no listener for that event, Node's default behavior is to crash with a bare, unhelpful stack trace. `start()`'s promise rejects with an actionable message for that one pre-listen failure and propagates it to `bootstrap().catch()` in `index.js`, the same place `requireTls`'s synchronous missing-certs error already lands. It does *not* swallow a fault that happens after a successful bind (a `settled` flag guards this) — that still crashes the process the old way, on purpose, so Docker's `restart: unless-stopped` kicks in rather than leaving a dead listener silently in place. `465` (SMTPS/implicit TLS) is deliberately absent from `SMTP_PORT_OPTIONS` in `web/api.js` — `smtp.js` hardcodes `secure: false`, and a client expecting an immediate TLS handshake on that port would just get a broken connection; that's a protocol gap, not something a permission fix or a Docker port mapping can paper over.

**`shutdown.js` exists only to break a cycle, and its `shutdown()` is safe to call twice.** The drain-then-`process.exit(0)` sequence (stop smtp, then queue, then web, bounded to 30s) used to live in `index.js`. `web/api.js`'s `POST /api/system/restart` ("Restart bridge" in the GUI, used to apply `smtpPort`/`requireTls` changes) needs that exact same sequence, but `api.js` can't import it from `index.js` without `index.js` → `web/server.js` → `api.js` → `index.js` becoming a real cycle at the top level. `shutdown.js` sits below both: `index.js`'s SIGTERM/SIGINT handlers and `api.js`'s restart handler both import *it*, and it imports `smtp`/`queue`/`web/server.js` itself — the resulting cycle (`shutdown.js` → `web/server.js` → `api.js` → `shutdown.js`) is fine because none of the three call into it at module-evaluation time, only later from inside a request/signal handler, well after the whole graph has finished loading. The `shuttingDown` guard means both callers racing (e.g. a restart click during a SIGTERM-triggered shutdown) collapse into one drain, not two.

**`POST /api/system/restart` responds before calling `shutdown()`, via `setImmediate`.** The HTTP response has to actually reach the browser before `web.stop()` starts closing connections — sending it synchronously and then immediately tearing down in the same tick risks the response never flushing. This only actually restarts the process under something that restarts it automatically (Docker's `restart: unless-stopped`, systemd, ...); under a bare `npm start` it just exits, which the GUI has no way to detect.

**Web layer never spreads `store.state`.** `web/api.js`'s `projectState()` names every field explicitly. `state.json` holds `web.passwordHash`, `web.sessionSecret`, and `oauth.refreshToken` — any of those reaching the browser is a real credential leak, not a cosmetic bug. If you add a field to `state.json`, it does *not* automatically become visible to the GUI, and that's intentional — add it to `projectState()` explicitly if it should be.

**Session cookie key derives from the password hash**, not a stored session table: `HMAC(sessionSecret, passwordHash)`. Changing the password invalidates every existing session as a side effect, with no revocation list to maintain. `handlePasswordChange` issues a fresh cookie for the caller's own request afterward — otherwise the user who just changed their password would be logged out by their own action.

**Device code flow is fire-and-forget from the API's perspective.** `oauth.beginDeviceCodeFlow()` returns as soon as Microsoft issues a code (one fast HTTP round trip) and runs the polling loop (up to ~15 min) in the background; it does not block the HTTP request. Progress is pushed over SSE (`auth` events) and mirrored in `oauth.pendingDeviceCode()`. Don't `await` the old blocking pattern back in — `POST /api/oauth/device/start` needs to return in well under a second.

**`/api/state` carries a fresh CSRF token in every response, not just `/api/login` and `/api/password`.** `app.js`'s module-scoped `csrfToken` variable resets on every page load, but a page load with a still-valid session cookie goes straight to `GET /api/state` (`boot()`), never touching `/api/login`. If `/api/state` didn't hand back a token too, that variable stayed `null` for the rest of the session and every mutating request — e.g. "Save & connect" on the client-id form — failed with a bare `403 { error: 'csrf' }` despite a perfectly valid cookie. `app.js`'s `api()` helper picks up `csrfToken` from any response that has one, not just login/password, so this self-heals on the next `/api/state` poll too.

**The OAuth client ID has two sources, and only one of them is correct to read from `oauth.js`.** `config.oauth.clientId` comes from `BRIDGE_CLIENT_ID`, read once at process start. `state.oauth.clientId` is what the GUI writes (`POST /api/oauth/client` → `oauth.setClientId`), seeded from `config.oauth.clientId` only on first run. Always go through `oauth.currentClientId()` (state first, config as fallback) — never read `config.oauth.clientId` directly in a request builder. `tokenParams()` used to do exactly that, so every token request was built from the env value while the GUI silently wrote somewhere else; with `BRIDGE_CLIENT_ID` unset (the normal case for anyone using the GUI), the request went out with an empty `client_id` and Microsoft rejected it with AADSTS900144. The device-start gate in `web/api.js` and `projectState()`'s exposed `clientId` field must use the same accessor as the request builder, or the gate and the actual request can disagree again.

## Testing

`test/fake-graph.js` mocks both Microsoft endpoints behind one `http.Server`, controllable via `setMode()` (`success`, `invalid_base64`, `send_as_denied`, `too_large`, `unauthorized`, `server_error`, `quota`, `rate_limited`, `hang`, `reset`, `invalid_grant`) and `setDevicePendingCount()`. It's picked up by `node --test`'s file discovery (any `.js` under a `test/` directory) but contributes zero assertions itself — that's expected, not a bug.

Three more knobs cover the alias-forcing send path: `setAliases(addresses)` and `setEnforceFrom(bool)` together make the mock actually inspect a request's `From:` (parsed with the real `unfoldHeaders`/`extractAddrSpec` from `src/mime.js`, not a hand-rolled regex — keeps the mock honest and free) and reject anything not in `aliases` with `send_as_denied`, both **off by default** so every test written before this feature keeps passing unchanged. `setHonorPatchFrom(bool)` simulates the one thing this mock can't know for real: whether Graph actually applies a `PATCH .../messages/{id} { from }` for a personal account's alias. `false` pins a created draft's `from` to the primary address regardless of what the MIME said and refuses to let `PATCH` change it — reproducing the pessimistic public report `graph.js`'s draft-path comment describes — so a test can exercise the degrade-but-still-deliver path without an emulator that guesses at undocumented Microsoft behavior. `_reset` clears all three (plus `drafts`) between test files; a fake-graph knob left set from a prior file is exactly the kind of leak this exists to prevent.

When testing timing-sensitive queue behavior manually, inject a fake clock via `createQueue({ clock })` where `clock.sleep(ms)` resolves quickly while still advancing a virtual `now()` — a clock whose `sleep()` is fast but whose `now()` stays real will make backoff waits busy-poll instead of accelerating, since `queue.js`'s age/backoff math is computed from real deltas.

## Known platform gaps

Real `SIGTERM` delivery cannot be exercised on Windows dev machines (Windows has no POSIX signals; `child.kill('SIGTERM')` hard-terminates instead of invoking the handler). `SIGINT` is emulated on Windows and exercises the same `shutdown()` path, but even that has been unreliable against piped child processes in testing here. Verify graceful shutdown manually against the real Linux container before relying on it.
